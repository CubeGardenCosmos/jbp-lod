## Implementation status

`VulkanLodRenderer.prepare` acquires the active runtime and frame-scoped provider targets, validates the target/device contract, obtains a reusable actual-game-frame slot, binds model/geometry/atlas/lightmap/fog resources and submits its pre-pass on the borrowed graphics queue. The offscreen schedule follows upstream `AbstractRenderPipeline.runPipeline`: draw the **previous opaque** command/position snapshot first, build HiZ and run traversal/cull/current command generation, draw the current **temporal opaque** additions, then the current distance-sorted **translucent** region. `LodOpaqueHistory` preserves opaque commands and positions GPU-side for the next frame; first-frame history is empty. The current opaque and temporal spans are not blindly drawn together, since upstream temporal commands are a subset of the newly generated opaque span. `LodDrawSequence` records the ordering contract.
 
`MixinDefaultChunkRenderer` now forces CUTOUT at the `prepare(ChunkRenderListIterable, CameraTransform, boolean)` TAIL when either the V1 probe is enabled or the renderer is enabled with an active runtime. Its render HEAD no longer gates LOD preparation on Sodium's original `shouldDraw`. Java 25 `javap` inspection of locked Sodium `mc26.3-0.9.2-fabric` establishes the empty-list path: game render-state extraction calls Sodium preparation; `RenderSectionManager.prepareChunkRendering` calls `ChunkRenderer.prepare` without a list-emptiness gate; `DefaultChunkRenderer.prepare` resets the draw flags even for an empty iterator before the injected TAIL. The OPAQUE group dispatches CUTOUT, and forcing its flag lets the empty render loop reach `ShaderChunkRenderer.end`, preserving the existing V1/draw injection. This is source/bytecode reachability evidence, not game execution evidence.

## Near-zone speckle: vanilla overlap (NearZoneFix)

Symptom: on the mountain near the camera, brown/green/grey speckle where vanilla terrain should be clean (`local://pasted-image-31522ba544fcaa5.png`, `local://pasted-image-2fc398cf87790980.png`).

Upstream reference (read-only, `mods/voxy`; source: https://github.com/MCRcortex/voxy, fetched via GitHub API):
- `core/AbstractRenderPipeline.java` `initDepthStencil`: vanilla depth is copied into the attachment; where vanilla geometry exists LOD is excluded by a stencil bit (stencil 0), and LOD draws only with `GL_EQUAL 1`, so LOD never shares a pixel with vanilla terrain.
- `core/rendering/bounding/BoundRenderer.java`: back faces of loaded-chunk AABBs are rasterised into `depthBoundingBuffer`; `lod/gl46/quads.frag` discards LOD fragments nearer than that bound (`DEPTH_SCALAR_COMPARE(gl_FragCoord.z, depthTex)`), so LOD is not drawn inside loaded-chunk volumes.
- `mixin/sodium/MixinDefaultChunkRenderer.java`: LOD is drawn inside the CUTOUT pass after Sodium's draws.

Port state before this fix:
- No stencil mask and no bounding-depth discard (`grep depthTex|DEPTH_SCALAR_COMPARE` in `resources/.../lod/gl46/quads.frag` finds nothing).
- `LodOffscreenPass` and `VulkanLodRenderer` test LOD against the previous-frame seed (`LodDepthTarget`, `LESS_OR_EQUAL`/`GREATER_OR_EQUAL`), and `offscreen_composite.frag` tests the reprojected LOD depth against the current game depth with the same compare, with no bias.
- Cause (hypothesis, not yet observed on a GPU): LOD surfaces coincident with vanilla faces in the near zone pass the equal-depth test on some pixels and fail on others, because the LOD and game projections round differently. The result is a per-pixel mix of LOD and vanilla colours, which is the observed speckle.

Fix applied (StencilSeedFix, upstream Voxy `initDepthStencil` + `setup_stencil_depth.frag`):
- The offscreen seed is `VK_FORMAT_D32_SFLOAT_S8_UINT`, cleared each frame to depth FAR and stencil 1 (`LodDepthTarget.SEED_FORMAT`, `LodOffscreenPass.begin`).
- `LodDepthConvertPass` (`depth_convert.frag`) runs before the LOD draws. For each game-depth pixel that is not FAR it writes `gl_FragDepth = lodNear` (reverseZ ? 1 : 0) and stencil 0. Sky pixels (game depth == FAR) are discarded and keep stencil 1. Depth test ALWAYS, depth write on, stencil op (KEEP, KEEP, REPLACE), write mask 0xFF.
- The LOD draws (`draw`, `temporal`, `translucent`, `VulkanLodPipeline.Stencil.LOD_ON_SKY`) use stencil test EQUAL 1, reference 1, write mask 0, ops KEEP. LOD fragments therefore render only where vanilla is absent, so the coincident-depth race is removed rather than biased.
- The depth bias is removed entirely: `COINCIDENT_DEPTH_BIAS`, `coincidentBias()`, `biasedDepthAtDistance()`, the 3-argument `writeVec4`, and `gameParams.w`. `offscreen_composite.frag` writes `gl_FragDepth = clamp(screenDepth, 0, 1)`.
- Test: `LodCompositeDepthTest.coincidentLodDepthReprojectsOntoVanillaSurfaceWithoutBias` checks that LOD depth reprojects onto the vanilla surface within 1e-6 at w = 32..2048.

Known limits of the initial stencil fix (superseded in the investigation below):
- The initial composite ran inside the game's open CUTOUT scope and could not sample the attached game depth. Its previous-final-depth seed could include LOD itself, not just vanilla; treating that source as a vanilla mask was incorrect.
- A vanilla-only historical seed remains one frame old. Newly appearing vanilla geometry still relies on bounding exclusion and the current game depth test at composition.

Bounding depth (BoundingFix, upstream Voxy `BoundRenderer` + `chunkoutline/outline.vsh|fsh`):
- `MixinVisibleChunkCollector` records every built section Sodium visits (`RenderSectionFlags.MASK_IS_BUILT`) into `LodBoundingSectionStore`. `MixinRenderSectionManager` clears it at the start of each render-list build (`renderOutOfGraph` HEAD and the `VisibleChunkCollector` constructor in `readRenderListFromTree`). Both run on the render thread and only while the LOD runtime is active.
- `LodBoundingPass` rasterises one 16^3 cube per recorded section (`lod/bounding/bounding.vert|frag`) into a per-slot D32 target cleared to `inverseClearDepth` (reverse ? 1 : 0), with compare `furtherDepthCompare` (reverse ? LESS : GREATER), so each pixel keeps its farthest section bound. The shader culls sections outside the render distance, as upstream does.
- `quads.frag` samples that target at binding 9 and discards any LOD fragment where `DEPTH_SCALAR_COMPARE(gl_FragCoord.z, bound)` holds, which is upstream's `depthTex` gate.
- Deliberate difference: upstream rasterises back faces only. This port uses no face culling; the farthest face of each cube is the same back face, so the stored bound is the same.

### Traversal and temporal draw audit

Traversal follows upstream and selects a node or its children, not both in the same traversal. The renderer draws previous opaque commands and current temporal additions, not current opaque and temporal indiscriminately. A previous-parent/current-child overlap during refinement remains an intentional upstream one-frame transition; a persistent parent/child double selection was not established.

A concrete GPU data race was found in the cull raster shader: the vertex shader read the same section-visibility SSBO that fragment invocations updated. Upstream `cull/raster.vert` explicitly acknowledges this race. Vertex invocations can therefore see different visibility epochs and spuriously classify an already-visible section as temporal. The port now copies visibility once into the existing per-slot visibility scratch before rasterization, with transfer/graphics barriers, and reads the immutable copy at binding 4 while the fragment shader writes binding 2. This allocates no new per-frame buffer. `LodCullVisibilityTest` adds source-contract and compiled-descriptor regression coverage for normal and reverse-Z. No test execution is claimed here. This fixes nondeterministic temporal classification; its contribution to these screenshots remains GPU-unverified.

### Bounding, stencil and precision audit

The bound clear value, farthest-depth compare, reverse-Z discard direction, section unpack/range checks and projection conventions match the sealed upstream implementation. Quad section translation, float scaling, and the `0.00005` face expansion also match upstream. No evidence justified changing D32 precision, quantization, mip sampling, or applying a depth bias.

Stencil state is internally consistent: clear 1, seed replaces covered pixels with 0, LOD tests EQUAL 1 without writes. Correct stencil state alone does not establish that the seed contains the correct source pixels.

### Depth-seed feedback defect and closed-scope repair

The seed source was the borrowed game's **previous final depth**, not a vanilla-only depth image. The LOD composite writes its own projected depth into that same image. Thus a later seed can interpret previous LOD coverage as vanilla coverage, replace stencil with 0, and suppress LOD itself. With the pre-pass submitted before the pending game command buffer, a clear recorded in that pending buffer cannot make the seed current. This is a feedback loop, not a wrong GREATER/LESS bound comparison; it explains why adding an otherwise consistent stencil seed need not cure coverage noise.

The repair preserves a private vanilla-only depth snapshot before composing LOD. It must happen outside the backend's rendering scope: bytecode inspection showed `ShaderChunkRenderer.end` merely clears its active program and does **not** close Vulkan rendering. The actual safe boundary is `FrontendRenderPass.close`, whose completion callback ends backend rendering. The Sodium hook now defers the work to that boundary; an owned composite rendering scope loads/stores the borrowed game attachments after the snapshot. No backend-owned rendering scope is forcibly ended or reconstructed.

`LodVanillaDepthSnapshot` uses per-slot owned D32 targets and a fullscreen `texelFetch` → `gl_FragDepth` copy, so the borrowed game image does not require transfer-source usage. The renderer samples the latest captured vanilla snapshot across slots, resets history on resource rebuild, and clears to FAR/stencil 1 without sampling on first activation. Existing generation/slot retirement leases cover snapshots and borrowed views. `LodVanillaSeedHistoryTest` covers history selection/reset, source ordering, identity gating and retirement registration; shader compilation coverage includes the snapshot shader. These tests were added, not executed by this slice.

Confidence: high that previous-final-depth contamination and the visibility SSBO race are source defects; moderate that they dominate the supplied speckle. No post-fix GPU result is claimed, and initial pre-stencil noise cannot be attributed to the later seed alone. The new phase/level/bound captures are required to discriminate any remaining overlap or rejection.

`LodCompositeDepthTest` additionally evaluates strict normal/reverse-Z bound comparison mathematically: equal depth survives; nearer fragments discard; the inverse clear value never discards a valid [0,1] fragment. These are unit-level checks of shader conventions, not hardware depth evidence.

### Cause: the LOD masked itself with its own depth

The vanilla mask is a snapshot of the **borrowed game depth attachment**. The composite writes its reprojected LOD depth into that same attachment (`offscreen_composite.frag` writes `gl_FragDepth`; the composite pipeline had `depthWrite=true`). The seed pass then tests `depth == FAR` — so a pixel the LOD painted is read back as "vanilla", gets stencil 0, and rejects LOD on the *next* frames. The flicker and the coverage collapse are the duty cycle of that loop:

- Pre-commit the contamination was one frame old and the mask flipped parity every frame, so roughly half the true LOD area survived each frame (24.9k–59.4k observed ≈ half of the ~74k-pixel band a flat-world LOD plane can cover). That is the flicker the user reported first.
- After the snapshot change the seed is taken one frame *further* back (during the previous frame's composite), so the loop became even-parity: the LOD re-suppresses the same pixel set every frame and only pixels whose coverage changed survive (31–609 pixels). That is the current flicker plus the near-total coverage loss.

The stencil census corroborates the mask being *spatially* plausible (34% open) while the yield is 0.4% of it: the mask is not degenerate, it is self-inflicted.

### Fixes applied (source-level; pure-logic regression tests added)

1. `VulkanLodPipeline.State.composite` + `LodOffscreenPass`: the composite now **depth-tests but never depth-writes** the borrowed game depth. That attachment is the only source of the vanilla mask, so keeping it vanilla-only is the invariant the seed design already assumed. Vanilla geometry still occludes LOD through the depth test. Tests: `LodDepthSeedInvariantTest.compositeTestsDepthButNeverWritesItIntoTheBorrowedGameDepth`, `lodDepthInTheGameDepthMakesTheLodMaskItselfAndStopDrawing` (models the parity loop), plus a source contract in `LodVanillaSeedHistoryTest`.
2. `LodDepthConvertPass.seedClearStencil`: with no snapshot yet, the seed clear writes stencil **0**, not 1. Previously the first frames had no vanilla mask at all, drew LOD over the whole screen and injected LOD depth into the borrowed attachment, seeding the loop from a clean start. Tests: `seedClearSuppressesLodUntilAVanillaSnapshotExists`, source contract as above.
3. `VulkanLodRenderer.visibilityFrames`: the visibility frame id now counts **recorded LOD frames**, not `GameVulkan.frameId()` (a submission epoch that can advance more than once per rendered frame or be skipped). The shaders' `previous == frameId - 1` classification is now exact. A skipped frame still classifies every visible section as a temporal addition, i.e. over-draw for one frame, never a dropped section. Tests: `LodVisibilityTest` (encode/classify/wrap/skipped-frame, plus a source contract that `raster.vert` and `cmdgen.comp` use the same masks).
4. `LodIndexBuffer`: the region between the quad pattern and the 786432-element cube offset is now zeroed instead of left as uninitialised host-visible memory.
5. Diagnostics (dev-only, behind `-Djbp.lod.debugReadback`): one log line per sample with **all three pass counts, the recorded frame id and the per-frame visibility census** (`visibleNow`/`previousFlagSet`/`temporalNext`, read back from the section-visibility buffer), and each sample now captures **two consecutive frames** (120/121, 240/241, …) so adjacent-frame oscillation is visible in the log. Tests: `LodReadbackProbeTest` (pair schedule, census, capacity validation).

`LodReadbackProbe.VisibilityStats.temporalNext` is the set `cmdgen.comp` will classify as temporal on the next frame (`visibleThisFrame` with bit 31 clear). A section flipping between `previousFlagSet` and `temporalNext` on two consecutive lines *is* a toggling classification; equal numbers across a pair mean the classification is stable and any flicker must come from geometry/depth instead.

### Audited without finding a defect (this slice, source-level)

- **Per-frame-slot indexing.** Every slot-scoped resource use was traced (`LodFrameBuffers.beginCommands/clearDrawOutputs`, `LodOffscreenPass.colorImage/depthTarget/recordComposite`, `HizPyramid.record`, `LodBoundingPass.record`, `LodDepthConvertPass.record`, `LodVanillaDepthSnapshot.record`, `LodCullRasterPass.record`, executor `queueMetadata[frame]`/`visibilityOps[frame]`/`cleanerOutput[frame]`) and each is keyed by `slot.slotIndex()` or `checkSlot(slot.slotIndex())`. The shared `LodOpaqueHistory` is written at the end of a pre-pass and read at the start of the next, both on the one graphics queue.
- **HiZ.** The mip-0 FAR→NEAR patch was already removed; `hiz.comp` uses a min reduction under `USE_REVERSE_Z` (upstream hardcodes `max`, which is only valid for its standard-Z path), and `HizLayout.packedSize()` is `width << 16 | height` in texels, matching upstream `HiZBuffer.getPackedLevels` (the used class), not `HiZBuffer2`'s log2 packing. Removing the patch strictly *lowers* culling, and the command counts confirm it (18–26 → 33–134): the extra nodes cannot explain a pixel *loss*.
- **LOD projection / near-far.** `VanillaLodExternalTargetsProvider.lodProjection` matches upstream `VoxyRenderSystem.computeProjectionMat` term for term (near 8/16 by vanilla render distance, far 48000, reverse-Z near/far swap, zero-to-one `m22`/`m32`), and the same matrix feeds the traversal, cull raster, bounding pass and both draw sides, so the depth-based tests are self-consistent. `VulkanLodRenderer` refuses to change the convention after the executor is built.
- **Composite applied on some frames only.** `deferCutout` stores only the CUTOUT pass instance and `afterPassClosed` requires `pendingPass == pass` before it clears both fields and records, so a composite cannot run twice or against another pass; a missed close leaves a null pending pair and cannot leak the slot lease (the lease is taken in `prepare`, not in `record`). `reveal`/`release` paths clear the pair. Nothing here is per-frame-slot conditional, so the composite is not itself a flicker source.
- **TAA jitter.** Not a factor in this port: no `ShaderCompiler.compile` call site defines `TAA` or `TAA_PATCH`, and `quads3.vert` unconditionally sets `taaOffset = vec2(0.0)`, so no jitter is applied to the LOD draws, the cull raster or the traversal screen-space bounds. The `#ifdef TAA` branches in `screenspace.glsl`/`cull/raster.vert` are unreachable.
- **Render distance and screen-space threshold.** `renderDistanceSquared(16)` reproduces upstream's `(sectionRenderDistance*16*32)^2` default and `minimumScreenSpaceSize` reproduces `subDivisionSize^2/(width*height)`; the bounding pass uses vanilla `renderDistance*16` blocks as upstream. No cut differs.
- **Why the render list is small.** At the sample times the session holds 2000 nodes, 206 geometry slots and 152 parked child requests (`stats:` lines), i.e. the LOD tree is only ~1–3% populated after ten seconds. 14–56 selected sections are data availability, not a traversal cut. The readback confirms the selected commands are real: `cullDrawIndirectCommand.instanceCount` equals the render-list count and the first command of each region has sane `vertexOffset`/`firstInstance`.
- **`temporal` oscillation is spatial, not a pass schedule bug.** `temporal=0/0/7/0` across 120-frame-apart samples is the newly-visible set changing; the samples that *are* adjacent (the new pair scheme) are the ones that can show a toggling frame id.

## Opaque LOD alpha leaked packed metadata into coverage (2026-10-19; source-level fix, NOT GPU-verified)

Symptom (review of the 09:28 readback log, normal view): distant LoD ground beyond the vanilla edge
looked like sky even though the draw commands, culling and depth seed were sane.

### Evidence

- `quad_util.glsl` `makeRemainingAttributes` packs `face | lodLevel<<3 | hasAO<<6` into the opaque
  tinting alpha because `lighting.w` is 0 for non-translucent models (`tint` output alpha 0).
- `quads.frag` `computeColour` returns `colour + vec4(0,0,0, metadata/255)`, so the opaque fragment
  alpha reaching the offscreen target is the packed metadata byte.
- `offscreen_composite.frag` divides the accumulated colour by that alpha, and the composite pipeline
  blends `SRC_ALPHA / ONE_MINUS_SRC_ALPHA` into the game's 8-bit target
  (`VulkanLodPipeline.State.composite`), so opaque LoD was applied at `metadata/255` opacity:
  65/255 = 25% at level 0 up to 101/255 = 40% at level 4 with AO. The rest of the pixel stayed sky.
  Metadata 0 (face 0, level 0, no AO) was discarded outright by the composite's `alpha <= 0` test.
- Upstream Voxy never lets the packed byte reach the blend: `post/ssao.comp` reads it for the AO
  normal and then writes `ocolour.w = 1.0f`; its `blit_texture_cutout.frag` samples that
  alpha-cleared texture and blends at coverage 1. This port has no SSAO pass, so the reset was lost.

### Fix

`lod/gl46/quads.frag` resets `colour.a = 1.0f` after `computeColour` (the only consumer of the packed
bytes) and before `applyLodFog`, under `#ifndef TRANSLUCENT`, equivalent to upstream `ssao.comp`'s
`ocolour.w = 1.0f`. Consequences, all verified by pure-logic tests:

- Opaque and temporal draws reach the composite at alpha 1, so the division is the identity and the
  blended result is the LoD colour at any face/level/AO metadata value.
- Translucent draws keep their real texture alpha; the composite's division stays necessary because
  `SRC_ALPHA` blending onto transparent black stores a premultiplied aggregate (alpha 0.5 over the
  cleared target becomes `(0.5*C, 0.5)` and is recovered as `(C, 0.5)`).
- Pixels never written keep the clear value alpha 0 and are still discarded by the composite.
- Debug views and `-Djbp.lod.debugSolid` already wrote alpha 1.0, so their output is unchanged.
  Nothing else in this port read the packed alpha; the readback probe reports it as a statistic only.

Tests: `LodCompositeAlphaTest` models the draw blend, the packed metadata byte, the composite division
and the 8-bit composite blend, asserting full-coverage opaque output for every face (0–5), level (0–4)
and AO value, translucent alpha preservation, and the alpha-0 discard. `ShaderCompilerCoverageTest`
pins the shader contract (reset present, opaque-only, after `computeColour` and before the output).

### Readback probe cadence

`LodReadbackProbe` previously stopped after eight samples (four frame pairs 120 frames apart), all of
which fired in the first seconds before the world import produced distant sections; the 09:28
"low pixel yield" samples measured missing data, not a draw failure. It now takes the same four fast
pairs (120/121 … 480/481) and then one pair every 1800 frames (~30 s at 60 fps) up to 40 samples
(~8 minutes), so post-import samples are logged. `ColorStats` now also reports `nonzeroAlpha` and
`alphaShare` over the whole screen alongside the existing LoD colour `nonzeroPixels` count.

### Verification boundary

Source-level only; no game or GPU run was performed for this fix, so the visual result (distant LoD
at full opacity in the normal view, translucent LoD still blended) is **NOT GPU-verified**. The
`compileJava test lodJar` suite covers the shader compilation variants and the pure-logic models.

### Source-side near-range exclusion (deviation from upstream)

A section emits no draw commands when its **whole horizontal AABB** is nearer than the near-exclusion
radius. That radius is `min(options.getEffectiveRenderDistance() * 16, environmental fog end)` **minus**
an optional inward safety margin (`-Djbp.lod.nearExclusionMarginBlocks`, default **0**). The farthest
point of the AABB is tested, so any section containing the radius still draws: that is the overlap
allowance and it cannot open a seam. The excluded disk is therefore never larger than the region Sodium
guarantees to draw. The fixed defect that made the original `* 16 + 16` form wrong is documented in
"White ring at the vanilla edge" below. The radius is written every frame into the std140 tail padding of
`SceneUniform` (`exclusionRadius`, offset 92; the struct stays 96 bytes) and is consumed by `cmdgen.comp`;
camera and render-distance changes therefore apply on the next frame, including after a teleport. Stencil
seeding and the bounding-depth discard remain as safety. Rationale vs upstream Voxy: less near-range LOD
overdraw, no one-frame lag after teleport/RD change, less vertex and fill cost. Pure-logic predicate:
`LodNearExclusion` + `LodNearExclusionTest` (margin defaults/clamp, RD 2→8, teleport, AABB farthest-point
vs radius, LOD-level size, no-hole invariant, environmental-fog clamp, alignment-ring regression);
`LodSceneUniformTest` pins the 92/96 byte layout.

### White ring at the vanilla edge: discrimination and fix (2026-10-19, llvmpipe)

Symptom: a thin, flickering, camera-relative bright ring at the vanilla render-distance edge. The
candidates in the ticket (fog hand-off, a square-vs-circle seam, stencil/bounding lag, bright boundary
side faces, translucent coverage, clouds/sky) were discriminated on llvmpipe (854x480, RD 2, position E)
with the dev harness, `debugView=pass|bound|stencil|level|texture|light|face|normal` and a top-down
camera (`tp -1125.59 above:80 108.80 -90 89`), one client per debug view.

**Ruled out.** Fog is not the cause. `-Djbp.lod.debugFog=true` logs the hand-off at the shared
`FogRenderer.setupFog` RETURN injection: our priority-900 mixin runs first, so Sodium's own
`FogRendererMixin` capture sees the extended values, e.g.

```
[JBP-LOD] fog hand-off: data env=0.0..1024.0 rd=28.0..32.0
                                sodium env=1.0E8..1.0E8 rd=1.0E9..1.0E9 cull=1.0E8
```

(the first line is the pre-runtime frame; once a runtime is active the captured values are extended).
Vanilla terrain, the LOD fog block and Sodium's cull distance therefore all use the extended range, and
the LOD fragment shader's `applyLodFog` receives an empty range. The bright arc that is visible at the
horizon in the RD2 high-camera screenshots (`ring_baseline_1.png`) is **snow terrain**, not a seam: at
the same pixels `debugView=texture` shows raw atlas snow `(249,255,255)` (the snow.png tile is

`debugView=pass` shows previous-frame opaque geometry, and `bound`/`stencil` show the fragments survive;
none of the debug views shows fog, a gap, or a fixed-function reject at that arc. Clouds/sky and
translucent coverage are also excluded (pass view has no translucent/blue arc pixels).

**Root cause.** The near-exclusion radius was `renderDistanceChunks * 16 + margin` (RD 2: 48 blocks).
Sodium's traversal/search distance is `min(renderDistanceChunks * 16, cullDistance + 0.5)` (RD 2:
32 blocks), so vanilla coverage is only guaranteed inside the **32-block disk** (the loaded chunk grid is
a square and the LOD section grid is 32-block quantised, but neither guarantees coverage outside the
disk). The 48-block excluded disk therefore reached past the region vanilla draws. Whether the
32-block section containing the radius is drawn depends on the camera's position inside the section:
with the section's inner edge beyond 32 blocks, the annulus between the vanilla disk and the first drawn
LOD section is drawn by neither - a circular, camera-relative hole ring. Because the camera's offset
inside a 32-block section changes that annulus (0 to a full 32-block section in the 1D regression model),
the ring changes shape as the player moves: the observed flicker.

**Fix.** `LodNearExclusion.radiusBlocks(renderDistanceChunks, environmentalFogEnd)` now returns
`min(renderDistanceChunks * 16, fogEnd) - margin` (margin default 0; the environment fog end is read
from the same Sodium `FogParameters` used by the frame, so underwater/blindness fog culls vanilla and the
exclusion disk shrink together). A section containing the radius always draws, so the first drawn LOD
section starts at or inside the vanilla disk and the union covers every block vanilla cannot draw.
`DEFAULT_MARGIN_BLOCKS` is now 0 and the property only pulls the disk further inward (it is never added
outward). The shader predicate is unchanged.

## Black hillside masses: missing-section and new-section light semantics (2026-10-19, llvmpipe)

Symptom after the SkyLightFallback slice: at Main's camera the LOD still drew large pure-black masses
over hillside/slope side faces while only ridge tops and tree tops were lit. DarkLightFix measured
52/81/93/98% zero air-light at LOD levels 1/2/3/4 and attributed the residual to upstream `Mipper`
("faithful"). Every light semantic was therefore re-checked against `mods/voxy` (sealed 263) instead of
being accepted.

**Verified faithful, unchanged.**

- `WorldVoxilizedSectionMipper.mip` / `Mipper.mip`: opacity-first selection; ties use the call-site
  marker bits `x<<2 | y<<1 | z` (x > y > z); a mixed cell returns the winning opaque child word,
  including that child's own light; only an all-air octet averages block light down and sky light up.
  jbp `VoxelHierarchy.mip` matches all three points.
- Visible-face light: `RenderDataFactory`/`SectionMesherCore` copy `nextModel & LM` (the adjacent
  voxel's light) for opaque faces. A mixed mip cell is opaque, so its faces against other opaque cells
  are culled; a rendered face reads a genuinely air (or non-opaque) neighbour cell. The zero-air-light
  percentages therefore count cave/underground air too and do not by themselves blacken visible faces.
- Shader: light is `sky | block << 4` (sky low nibble); `getLightmapUv` maps u = block, v = sky to
  16x16 texel centres; `LIGHTING_SAMPLER_BINDING` (7) is `gameRenderer.levelLightmap()` with a
  linear/clamped single-level sampler; `interData.y` carries the sampled lightmap * face tint exactly
  as upstream's non-patched path. The `debugView=light` frame localised the black pixels to lightmap
  14-24/255 (face-tinted); the atlas (`texture` view) was not black there.
- Stored data that exists is correct: an offline RocksDB scan of the exposed level-0 surface in
  `/tmp/jbp-lod-cache-light2` reports 93-100% of top-face neighbour air at sky 15 (0% zero in all
  four samples) and 77-100% of side-neighbour air (13.8% zero at one cliff-edge sample, 0-2.5% at the
  others).

**Root cause, two deviations from upstream.**

1. *Absent neighbour section.* Upstream `ActiveSectionTracker.acquire` fills a storage miss with
   `Mapper.composeMappingId((byte) 15, 0, 0)` (air at full sky light). jbp returned
   `new long[32*32*32]` (air at sky 0), so every face on the boundary of the stored LoD region took
   light 0. Fix: `SectionMesher.sectionSource` maps a missing payload to a shared read-only
   `MISSING_SECTION_AIR` filled with air/sky-15.
2. *Never-written section payload.* Upstream creates a missing `WorldSection` through the same
   acquire path (air/sky-15 fill) and only then inserts the captured 16^3 chunk into its octant. jbp's
   `VoxelHierarchyWriter` allocated a zero array, so every chunk octant the capture had not reached
   stayed air at sky 0. Offline octant scan of the pre-fix cache: level 0 576/1,654 stored sections
   had at least one all-zero octant (290 with 4, 182 with 6); level 1 165/291; level 2 60/74; level 3
   18/21; level 4 8/8. Fix: `VoxelHierarchy.emptySection()` (air/sky-15) is the initial payload for a
   missing stored section.

Both fixes are semantic ports; no shader, atlas, mesher-selection or mip change was needed. Stale caches
written before the fix still contain the zero octants (the payload has no version marker yet); a fresh
capture/import is required, which the acceptance run below used. The same offline octant scan of the
fresh post-fix cache finds zero all-zero octants at levels 1-4 and 13/3,384 at level 0 (those are
written cave chunks whose air really is sky 0), i.e. the initial-payload fix is effective and the
remaining dark pixels are not missing data.

## Pale semi-transparent rectangles over the plain: translucent mip bleed + LoD fog tint (2026-10-19; root cause from user RTX 3060 Ti screenshots, fix source/test only)

Symptom (user, RTX 3060 Ti, superflat grass world, RD 2, flying/running while chunks load): large
pale blue-grey **semi-transparent axis-aligned rectangles** on the ground plane, several chunks wide,
at several different opacities, with a thin bright line along their far edge and a dashed line pattern
elsewhere; they sweep/flicker as terrain loads. Nothing in jbp-lod animates or fades, so the shape and
the fade are both unintended.

**Pixel evidence from the user's two screenshots** (`/tmp/rect1.png`, 1498x1080; `/tmp/rect2.png`,
1798x986 — copies of the pasted images, analysed numerically because this worker cannot view images):

| measurement | value |
| --- | --- |
| grass baseline (plain, outside the rectangles) | ~(84, 110, 52) sRGB |
| overlay colour solved per channel, assuming one uniform colour | **(169-178, 197-204, 251-260) = the frame's sky/fog colour (173, 203, 255)** |
| per-quad alpha, rect2 large quad interior (600x130 px) | median **0.596**, p10-p90 0.579-0.605, min 0.570 max 0.623 (const **within** the quad) |
| per-quad alpha, rect1 left quad | ~0.44 (channel-consistent 0.43/0.42/0.44 for the sky colour) |
| other rect1 regions | ~0.30 and ~0.15 |
| prediction of the blend `out = a*sky + (1-a)*grass` at a=0.596 | (137, 166, 174); observed (136, 163, 172) |

| pure sky pixels below y=350 in rect2 | 1,269, including a 1-2 px line at the quad's far edge (y=410) and dashed rows at y=578-588 |

The rectangles are **ground-plane quads in perspective**, with **constant alpha per quad** and a
**sky-coloured RGB**. The composite is opaque (the LOD target's alpha is 1 after a translucent draw
blends over opaque LOD terrain), so the "transparency" the user sees is the source texture's alpha
inside the LOD target, not the composite's alpha.

**Root cause, three parts.**

1. *Translucent mip bleed (upstream Voxy semantics).* `VoxelHierarchy.mip` ports `Mipper`: it skips air
   and picks the child with the highest light dampening. A glass/water/ice block has dampening 0-1 and
   therefore wins any cell that also contains air. **One** such block from a village, pond or structure
   promotes its whole mip cell at every coarser level (level 1 = 2 blocks/cell, level 4 = 16 blocks/cell;
   a merged face can span up to 16 cells = 32-256 blocks). Those quads are `isTranslucent`, so they are
   emitted into the translucent face range and alpha-blended over the opaque LOD terrain: the grass
   texture visible "through" the rectangle is the LOD target's own opaque grass. Upstream's own
   `Mipper` TODOs note the missing opacity/coverage weighting.
2. *LoD fog tint.* `quads.frag` applies `FogUniform` (environmental range) per fragment. The fog policy
   extends vanilla/Sodium fog while the runtime is active, but the LoD block was derived from the
   captured Sodium `FogParameters`, so any frame where that capture still held the unextended range
   (the activation frame logs `data env=0.0..1024.0` before the extension runs) tinted every fragment
   beyond the fog end to exactly the sky colour. Combined with (1), the cell-sized translucent quads
   become pale sky-coloured rectangles.
3. *Sky cracks at quad edges.* Rect2 has a 1-2 px pure-sky line exactly at the rectangle's far edge and
   dashed pure-sky rows at its near edge (measured above): the translucent quads do not join the
   surrounding opaque LOD coverage, so the uncovered pixels show the game's sky. These are the user's
   "thin bright line" and "dashed line pattern".

**Fixes (deviations documented).** The mip rule only affects new hierarchy writes; existing scope
caches keep the old parent cells until the world is re-captured or re-imported (there is no payload
version marker).

- `VoxelHierarchy.mip`: when the winning child is not fully opaque (dampening < 15), the cell keeps it
  only if at least **4 of its 8 children are non-air**; otherwise the cell becomes the usual averaged
  air. Real water/glass surfaces (half or more of the octet) survive all levels, isolated glass panes
  and one-block water sources no longer promote a parent cell. Leaves keep their upstream opacity 15
  override, so tree canopies are unchanged. This is a deliberate deviation from sealed Voxy 263; the
  opacity-first order, x>y>z tie priority and light averaging are unchanged.
- `LodFogPolicy.lodFog(renderEnabled, runtimeActive, captured)`: while the extension policy is active
  the LoD uniform is written as `Fog.disabled()` instead of trusting the captured Sodium range. The
  renderer calls it for every draw descriptor; the LoD can no longer inherit vanilla distance fog on
  an activation frame or in a build/driver state with a different capture order.
- Dev diagnostics: `-Djbp.lod.debugFog` also logs the LoD fog block once (`LOD fog uniform: start=...
  end=... color=...`); `SectionMesher` logs the first translucent mesh
  (`First section meshed with translucent quads: N at <section>`); `BuiltSection.translucentQuadCount()`
  exposes the translucent face range for diagnostics and tests.

**Verification boundary (honest).** The artifact was **not reproduced end-to-end on llvmpipe** in this
slice. The flat test world contains grass/dirt/bedrock only; the `/fill` water/glass commands first
targeted chunks the server did not have loaded, and an offline scan of the saved region files found
**0 `minecraft:water` strings and 1 glass string**, i.e. the fills did not reach the world. Every run
therefore reported `translucent=0` draw commands and no `First section meshed with translucent quads`
line (runs 1-6; e.g. run 6 imported 14,976 sections, meshed 9,979, 6,123 non-empty, 165 published
