# JBP-LOD V3 shared buffer and compute contract

Status: source-level implementation contract for V3/V4 integration, not game/GPU evidence. It is derived from the sealed Voxy shader sources (`lod/gl46/bindings.glsl`, `section.glsl`, `cmdgen.comp`, `prep.comp`, `buildtranslucents.comp`, `quad_format.glsl`, and `MDICSectionRenderer.java`). `mods/voxy` remains read-only. All multibyte scalar fields below are 32-bit little-endian words as observed on the supported JVM targets; shader `std430` arrays use the stated byte strides. No per-frame queue/device idle or CPU readback of draw counts/geometry is permitted. Retired traversal requests and cleaner positions are explicitly host-visible control feedback, not terrain-output correctness evidence.

## Ownership and frame lifetime

- `GameVulkan` is the sole source of `VkDevice`, `VmaAllocator`, queues and command buffers. JBP-LOD borrows these; it MUST NOT create/destroy a device, allocator, game queue, or borrowed command buffer.
- A V3 `GpuBuffer` owns only its VMA buffer/allocation and mapping it explicitly requested. It exposes handle, byte capacity, usage, and allocation/mapping properties; closing destroys only its own allocation. An allocation is not resized in place: growth creates a replacement, preserves/copies requested contents if required, and retires the old allocation only after every submitted use has completed.
- Mutable per-frame indirect/count/scratch outputs are frame-in-flight resources, not one shared buffer overwritten while submitted work may still consume it. A frame slot is reused only after its existing completion token proves retirement. V3 does not wait for the whole device/queue or read results to the CPU to establish this.
- Upload/staging writes are host-side inputs; GPU-generated section/visibility/command data remains GPU-resident. Resource destruction and scope closure are deferred until the owning session's submitted work has retired.

## Section geometry and shader ABI

- `SectionMeta` is exactly 32 bytes: `a[4]` at byte 0 and `b[4]` at byte 16 (`uvec4 a; uvec4 b;`, `std430`). Fields: `a.x,a.y` are packed section position; detail is `a.x >> 28`; `a.z` stores 5-bit XYZ AABB offsets in bits 0/5/10 and sizes-minus-one in bits 15/20/25; `a.w` is the first packed-quad index. `b.x` low/high 16 bits are translucent/double-sided quad counts. `b.y`, `b.z`, `b.w` each pack low/high 16-bit face counts in order down/up, north/south, west/east. Counts are quads, not vertices or bytes.
- Each source quad is exactly 8 bytes / two 32-bit words (`ivec2`/`uvec2` fallback in `quad_format.glsl`); the shader's packed bit layout is unchanged. Geometry offsets in `SectionMeta.a.w`, draw metadata and quad arrays are quad indices. No conversion to meshlets, CPU-expanded vertices, or alternate mesh format is part of this contract.
- The section metadata producer and packed-quad producer MUST preserve field/bit patterns from Voxy. Geometry data may be copied from staging to device-local storage, but the GPU format remains byte-for-byte compatible with the upstream shaders.
- `positionScratch[drawId]` contains the original two-word packed section position (8-byte stride); `drawId` is `gl_BaseInstance` and selects both the section position and section lookup for the vertex shader.

## Indirect data layouts

- Every indexed draw command matches Vulkan `VkDrawIndexedIndirectCommand` exactly: 20 bytes, five words `{indexCount:u32, instanceCount:u32, firstIndex:u32, vertexOffset:i32, firstInstance:u32}`. For a section with `quadCount`, `indexCount = quadCount * 6`, `instanceCount = 1`, `firstIndex = 0`, `vertexOffset = quadStart * 4` (signed 32-bit), `firstInstance = drawId`. It relies on the same shared 4-vertices-per-quad index pattern as Voxy.
- The indirect command allocation is divided into opaque `[0,400000)`, translucent `[400000,500000)`, and temporal opaque `[500000,600000)` commands. These are upstream draw-count capacities; their Vulkan byte offsets are the respective command index times 20. A count must remain within its capacity; overflow must be diagnosed, never silently written out of bounds.
- The 44-byte draw-count/control record has these `std430` offsets: dispatch X/Y/Z words at 0/4/8; opaque/translucent/temporal counts at 12/16/20; cull `VkDrawIndexedIndirectCommand` at 24..43. The prep pass initializes dispatch to `ceil(sectionCount/128),1,1`, the three output counts to zero, and cull command to `{36, sectionCount, 786432, 0, 0}` (upstream's `6*2*3`, section instances, `(1<<16)*6*2`, 0, 0). Vulkan dispatch-indirect consumes the first 12 bytes; draw-indirect-count reads the relevant command range and count word.
- Translucent ordering scratch begins with 1024 distance-bin counters, followed by up to 100000 draw IDs, preserving upstream's distance-to-camera binning (`1023 - min(distance,1023)`) and prefix-sum generation. `cmdgen` and translucent generation share the 32-bit count/index semantics and use the constants in `MDICSectionRenderer` (`TRANSLUCENT_WRITE_BASE=1024`).

## Required producer/consumer synchronization

All dependencies are recorded into the game's Vulkan command recording/submission path; synchronization is GPU-side and range-scoped. Implement with Synchronization2 (`VkBufferMemoryBarrier2`) where available through the locked game API; do not substitute a CPU wait.

| Producer | Consumer | Required dependency |
|---|---|---|
| Host writes mapped/coherent upload data | compute shader reads | `HOST` / `HOST_WRITE` → `COMPUTE_SHADER` / `SHADER_STORAGE_READ`; flush mapped ranges when allocation is not host-coherent. |
| `vkCmdCopyBuffer` staging upload | compute shader reads geometry/metadata/node inputs | `COPY` / `TRANSFER_WRITE` → `COMPUTE_SHADER` / `SHADER_STORAGE_READ` for the copied ranges. |
| Compute pass writes data read or updated by a later compute pass (section prep, traversal, visibility, prefix sum, translucent build, command generation) | subsequent compute shader | `COMPUTE_SHADER` / `SHADER_STORAGE_WRITE` → `COMPUTE_SHADER` / `SHADER_STORAGE_READ|SHADER_STORAGE_WRITE`, scoped to the actual dependent buffers/ranges. |
| Compute writes dispatch args | `vkCmdDispatchIndirect` | `COMPUTE_SHADER` / `SHADER_STORAGE_WRITE` → `DRAW_INDIRECT` / `INDIRECT_COMMAND_READ` for the first 12 bytes. |
| Compute writes draw commands/counts | `vkCmdDrawIndexedIndirectCount` | `COMPUTE_SHADER` / `SHADER_STORAGE_WRITE` → `DRAW_INDIRECT` / `INDIRECT_COMMAND_READ` for command and count ranges. |
| Compute writes shader-visible position/geometry metadata | vertex shader | `COMPUTE_SHADER` / `SHADER_STORAGE_WRITE` → `VERTEX_SHADER` / `SHADER_STORAGE_READ` for the consumed ranges. |

If V1's locked CUTOUT hook is already inside dynamic rendering, V3 compute MUST be recorded/submitted before that graphics scope; it cannot dispatch inside an open render scope. Queue-family ownership transfers/semaphores are required only if a later implementation actually selects a different queue/family; the current contract does not assume queues are distinct.

## Public integration surface

V3 packages are owned by the V3 implementation: `vk.gpu` owns VMA-backed resources/barriers, `data` owns immutable CPU ABI/layout values and section ingest, `compute` owns pass/pipeline recording and CPU reference semantics, and `storage` owns the scope-bound data session. V4 may depend on the stable ABI above, command/count buffer offsets and barrier producer/consumer rules; V4 must retain borrowed frame targets only for that frame and consume opaque/translucent/temporal command spans by their declared offsets/counts. V3 does not claim a usable draw pipeline, device capability, successful SPIR-V shader compilation, validation cleanliness, or actual LOD output until separately exercised.

### Current Java surface (implementation status)

- `vk.gpu.LodGpuBuffers(GameVulkan.Snapshot, framesInFlight, maxSections)` owns two-to-four `LodFrameBuffers` ring slots (`maxSections <= 200000`). `beginFrame(GameVulkan.frameId())` returns a reusable slot or `null` without waiting; repeated callbacks in the same game submission epoch retain the same result. `submitCommands(slot)` submits the ended pre-cutout command buffer to the borrowed game graphics queue. Only `afterGameSubmission()` may enqueue slot retirement markers, after the consuming game graphics work has been submitted; neither another LOD callback nor `close()` establishes that boundary. `slot.retireAfterUse(AutoCloseable)` and ring `retireAfterUse(slot, Runnable)` retain per-slot leases until that marker signals. `closeAfterRetirement(Runnable)` disables acquisition immediately and defers ring/runtime GPU destruction until every submitted slot retires, including slots awaiting the game submission. `GpuCompletion.close()` refuses to destroy an incomplete token. This is source-level lifetime logic, not exercised GPU/validation evidence; **pending: game smoke deferred by user**.
- `LodFrameBuffers.slotIndex()` indexes per-slot compute descriptors. It exposes the 96-byte graphics `sceneUniform`, independent 208-byte `traversalUniform`, 32-bit section visibility, 8-byte-per-draw position scratch, and queue/input buffers. `drawCommands()` holds 600000 20-byte records; `commandByteOffset(DrawRegion)` returns 0, 8000000, or 10000000 for opaque/translucent/temporal opaque. `drawCountByteOffset(DrawRegion)` returns 12/16/20. `drawCapacity(DrawRegion)` returns 400000/100000/100000. `clearDrawOutputs(commandBuffer)` transfer-zeroes command/control/translucent scratch before compute; its transfer→compute barriers are recorded immediately.
- `LodSectionGpuBuffers` owns fixed-capacity device-local geometry/metadata allocations. A successful `upload(game, commandBuffer, SectionGeometry)` records one immutable generation, returns an `UploadBatch` of staging owners, and records transfer→compute|vertex storage-read dependencies. It exposes active section/quad counts and uploaded byte ranges. A changed snapshot requires a new allocation generation; the old one must be retained through every consuming slot's retirement.
- `SectionIngest.pack(List<SectionInput>)` creates upstream-compatible `SectionGeometry`; `LodStorageSession.open(scope, worldIdentifier)` owns the scope and its RocksDB world backend, and exposes opaque section bytes, position iteration, ID mappings, `flush`, and `close`. `data.ingest.StoredVoxelSection` defines the JBP-LOD payload as 32768 little-endian packed voxel longs in `x | z << 5 | y << 10` order; it does not claim upstream `SaveLoadSystem3` compressed-storage compatibility.

The source also contains `LodComputeExecutor` scheduling, `HizPyramid`, asynchronous node/tree production and `JbpLodClient` → storage/session/runtime integration. `LodSession` installs `compute.SectionMesher`, whose upstream-derived face generation/scanline merging reads neighboring stored voxels and waits for published model IDs. Fabric chunk events plus a client dirty-section mixin feed game-thread immutable snapshots to the off-thread `LiveSectionProducer`; `VoxelHierarchy` assembles/mips all stored LOD levels, persists each update and calls `LodNodeService.onSectionUpdated` (including neighboring mesh invalidation). Accepted producer snapshots drain before node/storage closure. The production path is implemented in source, not yet game/GPU accepted. See [V3 source audit](V3.md); **pending: game smoke deferred by user**.

## Storage decision evidence boundary

The V3 storage decision record compares repository-evidenced RocksDB reuse against replacement and explicitly marks Android ABI/bionic/16 KiB suitability as pending where no JBP-LOD RocksDB binary or target-device result has been measured. ADR 0019 demonstrates that this repository's packaged native components have had real 4 KiB `PT_LOAD` alignments rejected on a 16 KiB Android page-size target, and that the runtime workaround is applied per binary with hashes; it is not evidence that RocksDB itself is incompatible or compatible. No unmeasured Android/native claim is promoted to a decision.
