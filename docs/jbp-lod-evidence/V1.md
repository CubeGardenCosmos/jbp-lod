# JBP-LOD V1 Vulkan bridge evidence

Date: 2026-10-18. Status: **代码就绪，待 Vulkan 实机验证**. The bridge compiled and ran on WSL2 llvmpipe, but V1's hardware/validation gate is not passed. This is a Vulkan bridge/timestamp/clear-marker spike only; it does not implement LOD compute or LOD drawing.

## Environment and Vulkan feasibility

- Host: Linux WSL2, kernel `6.18.33.2-microsoft-standard-WSL2`, x86_64, WSLg/Wayland; OpenJDK 25.0.4.1.1. `/dev/dxg` is present. `vulkaninfo` is not installed; probing used the Vulkan loader/ICD files directly.
- Loader/ICDs: `libvulkan.so.1`; lavapipe JSON `/usr/share/vulkan/icd.d/lvp_icd.x86_64.json` (API 1.4.354) and dzn JSON `/usr/share/vulkan/icd.d/dzn_icd.x86_64.json` (API 1.1.354). Before the run, `VK_ICD_FILENAMES`, `VK_INSTANCE_LAYERS`, and `VK_LAYER_PATH` were unset. Loader enumeration found llvmpipe and the Microsoft Direct3D12 Vulkan device for NVIDIA GeForce RTX 3060 Ti (`0x10de:0x2486`, API 1.2.354). Forcing dzn enumerated the NVIDIA device, but Minecraft's base feature check rejected it because `VK_KHR_push_descriptor` was missing; the V0 unforced client selected llvmpipe. The V1 probe run explicitly forced lavapipe.
- Validation layers: only `VK_LAYER_MESA_anti_lag` and `VK_LAYER_MESA_device_select` are installed; `VK_LAYER_KHRONOS_validation` is unavailable. The probe reports `validationLayerAvailable=false`, and no validation result is claimed.
- Prior sealed-reference check: a read-only `mods/voxy` forced-Vulkan launch hit its explicit guard (`Voxy does not presently support vulkan`) and fell back to OpenGL llvmpipe. `mods/voxy` was not edited.

## Bridge behavior observed

- Accessors now follow the locked bytecode path: `RenderSystem.getDevice()` → `FrontendGpuDevice.backend` (`FrontendGpuDeviceAccessor`) → `VulkanDevice`. `GameVulkan.current()` fails fast for a non-RenderPearl or non-Vulkan backend and snapshots the existing game instance, physical/device handles, graphics/compute/transfer queues and families, VMA handle, enabled feature/extension sets and device info. It borrows the game's device; it does not create or destroy it.
- CUTOUT uses `FrontendRenderPass.backend` → `VulkanRenderPass.commandBuffer`; `VulkanRenderPass.renderArea` is also exposed. The hook samples `DefaultChunkRenderer.render` at HEAD and inserts the marker immediately before `ShaderChunkRenderer.end(TerrainRenderPass)`. `TerrainRenderPass.getTarget()` supplied Vulkan color/depth views; `VulkanGpuTextureView`/`VulkanGpuTexture` supplied view, image and format, and the view supplied extent. Views are borrowed for that pass and not retained across frames. `ChunkRenderMatrices` projection/model-view values were logged.
- Current locked RenderPearl backend starts dynamic rendering before `DefaultChunkRenderer.render`; the CUTOUT hook therefore logs `renderScopeActive=true` and `insideDynamicRenderingScope=true`. Image layout and sample count are not exposed by a public per-image getter; for this locked implementation the rendering attachment info specifies `GENERAL` (`VK_IMAGE_LAYOUT_GENERAL`, 1) and single-sample. The bridge records that version-specific known state, not an independently queried layout. Recheck it when RenderPearl changes.
- At sampled frame 120 the log recorded color `RGBA8_UNORM` (`VkFormat=37`), depth `D32_FLOAT` (`VkFormat=126`), both 640×360, `GENERAL`, sample count 1, plus nonzero image/view/command-buffer handles. Graphics, compute, and transfer queues all reported the same handle and family 0 on llvmpipe. VMA was nonzero; `VK_EXT_debug_utils` was enabled and the game debug-utils facility reported enabled.
- The opt-in probe allocates a separate primary command buffer from the existing graphics family and submits a TOP_OF_PIPE timestamp to the existing graphics queue at CUTOUT HEAD. Inside Sodium's already-recording graphics command buffer it first records an 8×8 magenta `vkCmdClearAttachments` at render area origin `(0,0)`, then records a BOTTOM_OF_PIPE timestamp and optional debug label, all immediately before pass end. Frames 120, 240, and 360 each logged `visibleClearRegionRecorded=true`, `insideDynamicRenderingScope=true`, and `queryTimestampRecorded=true`. The magenta clear command is a debug-only visible marker; no LOD draw was issued.
- This needs a second command buffer and same-graphics-queue submit because the game graphics command buffer is already inside the dynamic-rendering scope at the CUTOUT method hook. The pre-pass submit is issued before the game's graphics command buffer is submitted later; the runtime logs record this order. The tested llvmpipe graphics/compute/transfer queues share one queue handle/family, so this timestamp-only spike needs no second queue, semaphore, or queue-family ownership transfer. It creates no compute-output memory hazard; eventual compute writes still require explicit barriers before graphics consumption.
- Source-level retirement follow-up (2026-10-19): `GameVulkan.frameId()` supplies one central game-submission epoch rather than a counter per LOD callback. Frame-slot retirement markers are queued only by the post-game-submission boundary, not by `beginFrame` or runtime `close`. Closed runtimes retain GPU owners and per-slot renderer leases until the relevant marker fences signal. Pure Java ring tests cover repeated callbacks, unavailable slots, boundary assignment, deferred leases and close-before-submission semantics; these additions have not been exercised in a game/GPU run here. **pending: game smoke deferred by user**.
- Locked bytecode inspection (`javap -p -c` on the Loom Minecraft 26.3 merged jar) identifies `VulkanCommandEncoder.submit()` as `endCommandBuffer` → submission semaphore signal → `VulkanQueue.Submission.close()` → next submission setup. `MixinVulkanCommandEncoder` publishes the boundary at normal return. `VulkanCommandEncoder.destroy()` closes its final submission and already calls `VulkanQueue.waitIdle()` before command-pool destruction; the additive mixin publishes pending markers immediately before that existing shutdown-only wait and polls retirement immediately after it, while the game VMA allocator/device still exist. JBP-LOD adds no queue/device wait in this retirement path. Mixin application and shutdown ordering remain unexercised in-game.
- LWJGL Java modules present in the actual runtime classpath (all 3.4.3): `lwjgl-vulkan`, `lwjgl-shaderc`, `lwjgl-spvc`, and `lwjgl-vma`. The probe resolved each module's class resource; `debug.log` also shows the shaderc, spvc, and VMA Linux native jars.
- Timestamp-query limitation: `timestampSupported=true`, but no `Vulkan order timestamps ... timestampOrderObserved=...` result was emitted during the run. At sampled frames 480 and 600 the probe reported query slots still in flight and deliberately issued no queue/device wait. The run therefore proves code-path recording and same-queue submission order, not completed GPU timestamp values. No Vulkan validation layer was available to check handles, layouts, or synchronization.

## Windows/Linux desktop human gate

Run on an actual Windows or Linux desktop GPU using the locked JDK 25/Minecraft/Fabric/Sodium build, current vendor Vulkan driver, and Khronos Vulkan SDK validation layer. Create a local world named `New World` first, or omit `--quickPlaySingleplayer` and enter a world manually. Do not force lavapipe or dzn for this gate.

Linux (from `mods/jbp-lod`):

```sh
export JAVA_TOOL_OPTIONS='-Djbp.lod.vkProbe=true -Djbp.lod.vkProbeInterval=120'
export VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation
./gradlew runClient --args='--graphicsBackend vulkan --width 1280 --height 720 --quickPlaySingleplayer "New World"' --console=plain 2>&1 | tee run/evidence/v1-linux-vulkan-validation.log
```

Windows PowerShell (from `mods/jbp-lod`):

```powershell
$env:JAVA_TOOL_OPTIONS = '-Djbp.lod.vkProbe=true -Djbp.lod.vkProbeInterval=120'
$env:VK_INSTANCE_LAYERS = 'VK_LAYER_KHRONOS_validation'
.\gradlew.bat runClient --args='--graphicsBackend vulkan --width 1280 --height 720 --quickPlaySingleplayer "New World"' --console=plain 2>&1 | Tee-Object -FilePath run/evidence/v1-windows-vulkan-validation.log
```

Keep the full client and debug logs and a screenshot showing the magenta top-left marker. Accept only if the selected device is the real hardware GPU; the probe reports validation available/requested; no Vulkan validation or RenderPearl handle/layout/synchronization errors occur; a completed query reports `timestampOrderObserved=true`; and the in-scope clear marker is visible. If timestamp results remain in flight, the human gate is still pending. Until that evidence exists, do not mark V1 passed or begin V2–V6.
